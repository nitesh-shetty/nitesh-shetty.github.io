If you’ve ever managed a Red Hat, Fedora, or AlmaLinux system, you’ve likely encountered the "Permissive vs. Enforcing" debate. Most people treat SELinux (Security-Enhanced Linux) as a nuisance to be disabled, but under the hood, it is one of the most sophisticated security architectures in modern computing.

In this post, we’re going under the hood to see how the Linux kernel actually implements Mandatory Access Control (MAC).

1. Beyond Permissions: What is SELinux?

Standard Linux uses DAC (Discretionary Access Control). If you own a file, you decide who sees it. If a process runs as root, it can see everything.

SELinux introduces MAC. It doesn't care if you are root. It asks: "Does the security policy explicitly allow this specific process 'type' to touch this specific file 'type'?"

2. The Architecture: Who Does the Work?

SELinux isn't a separate program; it is baked into the LSM (Linux Security Module) framework.

The LSM Hooks

Think of the kernel as a series of pipes. LSM hooks are sensors placed at every junction where a sensitive action occurs.

  • 1. Process calls open().
  • 2. Kernel checks standard DAC.
  • 3. If allowed, kernel hits an LSM Hook.
  • 4. Request is handed to the Security Server.

3. The Performance Secret: The AVC

Searching a rulebook for every system call would melt your CPU. The kernel uses the Access Vector Cache (AVC) to stay fast.

// AVC Logic:
1. Check AVC (Kernel Memory) -> HIT? Return Decision.
2. MISS? Consult Security Server -> Calculate -> Update AVC.

5. Summary

By confining processes to their own Type, SELinux ensures that even if an attacker exploits a bug in your Web Server, they are trapped in a sandbox.
